# Архитектура фронтенда Gridly

Руководство описывает структуру модулей Gridly и правила их расширения. Примеры показывают целевую структуру и применяются к модулям, которые уже работают по этим правилам.

## Где начать

| Что хотите изменить                   | Где искать                                                                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Как подключается экран или диалог     | Откройте родительский модуль. Главный компонент или `*.compose.ts(x)` показывает, как подключён потомок и откуда он получает данные.   |
| Как выглядит панель маршрутов         | Откройте `app/warehouse/warehouse-map/map-editor/route-toolbar`. Компонент и его CSS-модуль лежат рядом.                               |
| Как действие в редакторе меняет карту | Откройте `map.compose.tsx` в модуле карты и правила черновика в соседнем `draft/`.                                                     |
| Как читаются или записываются данные  | Найдите ресурс в `app/warehouse-data`. Он определяет ключи кэша, операции и применение событий. Формат ответа сервера ищите в его DTO. |
| Какие зависимости доступны экрану     | Начните с `index.ts` модуля и пропсов его главного компонента. Контракты общих зависимостей лежат в `src/ports`.                       |
| Как проверить изменение               | Ищите частный тест рядом с владельцем поведения, тест связи нескольких частей у общего родителя, браузерный сценарий в `tests/ui`.     |

## Принципы

1. **Каталог модуля показывает, кто его подключает.** Место отрисовки может отличаться. Например, `App` подключает общую форму настроек, а склад показывает её в своём диалоге.
2. **Импорты между модулями идут вниз по дереву.** Родитель импортирует публичные входы прямых потомков. Дочерний модуль не импортирует предков и соседей.
3. **У каждого значения один владелец записи.** Общим состоянием интерфейса владеет ближайший родитель, который связывает его потребителей. Серверным состоянием владеет ресурс. URL владеет параметрами навигации.
4. **Данные идут вниз, действия передаются через обработчики.** Дочерний компонент сообщает параметры действия. Владелец решает, как применить действие, и передаёт новый результат потребителям.
5. **Договорённости между ветками объявляются явно.** Модуль можно проверить через публичный вход с тестовыми данными. Связь между модулями проверяется у того, кто их собирает. [Передача состояния в React](https://react.dev/learn/sharing-state-between-components)

Дерево показывает границы на примере основных веток. У каждого самостоятельного модуля в `app` есть `index.ts`. Главный компонент называется по модулю. CSS-модуль носит имя своего компонента и лежит рядом. Небольшая часть одного экрана остаётся локальной функцией или соседним файлом. Отдельный модуль нужен, когда у части есть свой маршрут, самостоятельно проверяемое поведение или несколько реальных потребителей. При повторном использовании часть размещается у ближайшего общего владельца этих потребителей.

Для всех модулей приложения, включая вложенные модули `warehouse`, действует единая раскладка. Папку добавляют, когда у модуля есть файлы для неё.

| Место     | Что лежит внутри                                                                                                                                                                                                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Корень    | Публичный `index.ts` и главный компонент с именем модуля, например `Audit.tsx`. У главного компонента собственный CSS-модуль с тем же именем, если нужны локальные стили. Стили, общие для компонентов модуля, лежат в `shared.module.css` в корне. Файл сборки также лежит в корне, если нужен. |
| `api/`    | Запросы, мутации, схемы DTO и тесты этих схем.                                                                                                                                                                                                                                                  |
| `model/`  | Состояние экрана, правила формы, фильтры, преобразования данных и их тесты.                                                                                                                                                                                                                     |
| `lib/` | Чистые технические функции и алгоритмы, которые нужны модулю. |
| `config/` | Отдельные декларативные настройки и справочники. Константа, нужная одному файлу, остаётся рядом с кодом, который её использует.                                                                                                                                                                 |
| `ui/`     | У каждого вспомогательного компонента своя папка, даже если у него нет стилей. Например, `ui/AuditEvents/AuditEvents.tsx` импортирует `AuditEvents.module.css` из той же папки.                                                                                                                 |

Главный компонент лежит в корне модуля. Вспомогательный компонент `Details` лежит в `ui/Details/Details.tsx`. Его локальные стили лежат в `ui/Details/Details.module.css`. Если локальные стили не нужны, в папке остаётся компонент. Состояние, вычисления и справочники размещаются в `model/`, `lib/` и `config/` согласно их назначению.

Селекторы одного компонента принадлежат его CSS-модулю. Компоненты импортируют `shared.module.css`, когда им нужны общие стили своего модуля. Стили, которые используют несколько модулей приложения, принадлежат `shared/ui`. Компонент импортирует общий CSS-модуль, когда использует его классы. `bun run check:architecture` проверяет папки компонентов и запрещает импорт локальных стилей соседнего компонента.

`domain` содержит чистые модели и функции, которые используются несколькими модулями. Например, `Layout`, `Cell`, `Route` и геометрия сетки лежат в `domain/warehouse/layout`. Схемы REST и SSE принадлежат ресурсу. Адаптер переводит DTO в предметные значения на границе чтения и записи. `shared` содержит универсальные компоненты и технические функции. Прикладной код склада находится в `app`, его общие предметные правила в `domain`.

## Границы импортов и файлов сборки

| Откуда                                                                    | Что можно импортировать                                                                                  |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `src/main.tsx`                                                            | Публичный вход приложения.                                                                               |
| `index.ts`, главный компонент и `*.compose.ts` или `*.compose.tsx` модуля | Собственные файлы и публичные входы прямых дочерних модулей.                                             |
| Остальные файлы модуля                                                    | Файлы своего модуля.                                                                                     |
| Любой модуль внутри `app`                                                 | Публичные входы `domain`, `ports` и `shared`.                                                            |
| `domain`                                                                  | Чистые предметные функции и типы. У этого слоя нет зависимостей от React, окружения и ввода-вывода.      |
| `ports`                                                                   | Публичные типы `domain`, React и технические функции из `shared`. Реализации ресурсов принадлежат `app`. |
| `shared`                                                                  | Технические зависимости без импортов из `app`, `ports` и `domain`.                                       |

Владелец файла в `src/app` — ближайший каталог с `index.ts`. Служебная папка без такого файла относится к ближайшему модулю. Между модулями импортируют через `index.ts`. Внутри модуля импортируют нужный файл напрямую. Вход объявляет собственные публичные контракты. Входы внуков через родителя не реэкспортируются.

Сборка приложения в `src/app/composition/administration.compose.tsx` подключает `administration`, `audit`, `guest-links`, `orders`, `system`, `users` и `warehouses` через их публичные входы. Администрирование размещает эти экраны в слотах. Сборка передаёт диагностике события аудита и функции их отображения.

Файл `*.compose.ts(x)` соединяет прямых потомков и преобразует значения между их публичными контрактами. Правила черновика, состояние и серверные операции остаются во внутренних файлах владельца. Например, `map.compose.tsx` связывает редактор с областью карты, а `draft/layoutDraft.ts` применяет правку. Правило импорта действует для типов, реэкспортов и загрузки по `import()`.

### Пропсы, порты и слоты

- Пропсы используются для данных интерфейса и действий пользователя. Например, `RouteToolbar` получает маршруты и обработчик правки. Компонент объявляет нужную ему часть контракта и не зависит от реализации родителя.
- Именованный порт используется для долгоживущих зависимостей, нужных нескольким веткам. `src/ports/warehouse` объявляет тип `WarehouseData` и контекст для его передачи. Владелец области устанавливает провайдер. Адаптер экрана читает только нужные ему ресурсы и передаёт подготовленные данные в интерфейс. Например, экран заказов использует `Pick<WarehouseData, "orders" | "catalog">`. Глубокие дочерние компоненты получают данные от ближайшего владельца. Контекст внутри одного модуля допустим для его внутренних частей. [Передача контекста в React](https://react.dev/reference/react/useContext)
- Слот объявляет компонент, который размещает содержимое. Блок для слота импортирует его владелец. `WarehouseMap` может передать редактор в слот области карты, так как обе части являются её прямыми потомками. `MapEditor` подключает свою панель `RouteToolbar`. Для общего диалога настроек `App` передаёт складу и админке функцию отрисовки, принимающую выбранный склад. Каждая ветка управляет открытием своего диалога.

## Маршруты, сессия и доступ

- Роутер создаётся один раз. Каждый маршрутный модуль публикует лёгкое описание с идентификатором, относительным путём, правилами доступа и функцией ленивой загрузки. Вложенные пути известны до сопоставления URL. `index.ts` загружает собственный экран внутренним `import()` и не реэкспортирует его статически. Подключающий модуль использует тот же публичный вход. [Ленивая загрузка маршрутов React Router](https://reactrouter.com/api/data-routers/createBrowserRouter)
- Сборка роутера и типизированные функции построения ссылок используют одни и те же описания путей. `App` передаёт веткам нужные функции навигации через пропсы или именованный порт. Ссылки на соседей строятся без импорта их экранов.
- Аккаунт и песочница имеют разные ветки URL. Публичные страницы и гостевой портал подключаются отдельно от рабочего пространства. Гостевой доступ ограничен своим ресурсом и ключом кэша. Он не получает порт авторизованного рабочего пространства. Адаптер разбирает параметры URL и привязывает данные экрана к текущей области сессии. Сессионные запросы выполняет смонтированный адаптер экрана.
- Локальное состояние рабочего экрана имеет ключ из области сессии и идентификатора склада. Выход, смена аккаунта и переход между режимами закрывают старую область. Тихое обновление токена сохраняет идентификатор области и черновик. При закрытии области отменяются чтения, закрываются подписки, очищается её кэш и отбрасываются поздние ответы. `session` обрабатывает истечение авторизации и выход из того же аккаунта в соседней вкладке. Отмена ожидания ответа не определяет исход записи на сервере. [Сброс состояния в React](https://react.dev/learn/preserving-and-resetting-state)
- Маршрут проверяет общий доступ, ресурс даёт возможности для конкретного склада и операции. Сервер проверяет права при каждом чтении и записи. После входа приложение может восстановить исходный внутренний URL. Для отсутствующего склада показывается отдельное состояние. Скрытые действия не заменяют проверку на сервере.
- Диалог хранит состояние открытия у вызывающей ветки. Если состояние диалога нужно восстанавливать по ссылке, его хранит маршрут. Универсальный диалог из `shared/ui` отвечает за фокус и закрытие, а владелец формы решает, когда нужно подтвердить потерю черновика. Граница ветки обрабатывает ошибки отрисовки и загрузки экрана, включая ошибку ленивого чанка. Обновление страницы предлагается как явное действие. Владелец операции определяет её результат, а интерфейс, из которого её запустили, показывает сообщение.

## Владение данными и подписками

| Значение                                                  | Владелец                                                                                                                      |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Активный аккаунт, режим, обновление учётных данных        | `session`. `App` связывает сессию с адаптерами маршрутов и экземплярами ресурсов.                                             |
| Активный склад                                            | URL.                                                                                                                          |
| Список складов, настройки, сохранённая планировка, заказы | Ресурсы внутри `warehouse-data`. Каждый ресурс определяет свои ключи, запросы и операции.                                     |
| Общий поток событий склада                                | `warehouse-data/live`. Он разбирает события и передаёт их ресурсам, которые ими владеют. Транспорт лежит в `shared/realtime`. |
| Черновик, история правок и выбор клетки                   | `WarehouseMap`. Редактор, область карты и инспектор получают нужные части состояния.                                          |
| Открытая панель или локальный инструмент                  | Модуль панели или инструмента. Режим, который влияет и на редактор, и на область карты, принадлежит `WarehouseMap`.           |

TanStack Query хранит серверные данные. Ключ включает идентификатор области сессии, склад, ресурс и параметры, которые влияют на ответ. Токены в ключи не входят. Ресурс отвечает за применение результатов записи и событий. Если команда затрагивает связанные ресурсы, обработчик явно обновляет или инвалидирует их ключи. Например, изменение планировки инвалидирует представление, которое показывает привязки заказов к ячейкам, если эти привязки изменились. Экран вычисляет представления из ресурса и своего состояния. Изменения относятся к владельцу записи. [Инвалидация TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation)

При общем серверном потоке открывается одно соединение на пару из области сессии и склада. Потребители пользуются общим соединением. После ухода последнего потребителя соединение закрывается, а кэш может жить по настройкам TanStack Query. Поток обновляет только затронутые ресурсы. Движение роботов передаётся области карты отдельно от данных о маршрутах и черновике. При разрыве или неизвестном порядке событий ресурс запрашивает новый снимок.

Формы настроек одного склада читают сохранённые данные из одного ресурса. У каждого открытого диалога свой черновик. После обновления сохранённых данных открытый черновик сохраняется, а при записи сервер проверяет его исходную версию.

## Карта и сохранение

1. `MapViewport` отвечает за преобразование координат указателя в координаты сетки и сообщает о действии на карте. `WarehouseMap` интерпретирует действие с учётом режима. Выбор клетки обновляет инспектор, а правка маршрута или зоны обновляет черновик и предпросмотр.
2. `MapEditor` и его панели получают данные черновика и обработчики. Зоны, сохраняемые вместе с планировкой, входят в черновик. Если изменение размеров выполняется отдельной серверной командой, диалог размеров блокирует её до явного сохранения или отмены открытого черновика.
3. При сохранении ресурс получает снимок черновика и исходную версию. Снимок блокируется для правок до результата, а карту можно просматривать. Пока исход операции неизвестен, повторное нажатие не создаёт новую запись.
4. Навигация внутри карты сохраняет черновик. При выходе с несохранёнными правками пользователь подтверждает уход. Уже отправленная операция остаётся у ресурса. Если запись отклонена после ухода, ресурс сохраняет её снимок для возврата в течение той же сессии. После перезагрузки клиент читает серверный снимок и не отправляет запись автоматически. Восстановление локального черновика после закрытия вкладки, офлайн-очередь и автоматическое слияние требуют отдельных продуктовых требований.

Сервер проверяет исходную версию при записи. Для `If-Match` используется сильный ETag. ETag проверяется на совпадение. Порядок обновлений определяется монотонной ревизией, если её гарантирует сервер. При неизвестном порядке ресурс повторно читает снимок. Чтение, начатое до подтверждённой записи, не перезаписывает её результат. Контракт API определяет, при каком условии сервер принимает запись, как клиент подтверждает её исход и когда может безопасно повторить запрос. [Условные запросы HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match)

## Как расширять проект

### Добавить часть экрана

Начните с компонента, в котором пользователь увидит новую часть. Например, если в инспекторе карты нужен список предупреждений о клетке, добавьте его в `map-inspector`. Компонент, стили и локальные тесты держите рядом. Формат предупреждения, который нужен только инспектору, объявите у него.

Если предупреждения нужны в двух частях карты, их вычисление принадлежит `WarehouseMap`. Карта передаёт результат обеим частям. Когда предупреждение зависит от серверных данных, адаптер ресурса разбирает ответ и отдаёт предметное значение. Правила расчёта, которыми пользуются несколько модулей, лежат в `domain`.

### Добавить экран склада

1. Создайте дочерний модуль в `app/warehouse`. Назовите каталог по разделу, главный компонент по модулю, а его публичный вход `index.ts`.
2. Объявите в публичном входе описание маршрута и ленивую загрузку экрана. Подключите описание в `warehouse-routes.compose.ts`. Используйте то же описание для построения ссылок.
3. Перечислите данные и действия, которые нужны экрану. Возьмите из порта только эти ресурсы. Передайте компонентам готовые значения и обработчики.
4. Проверьте поведение модуля отдельно и открытие нового экрана по прямому URL. Если он меняет общие данные, проверьте, что другие потребители получают обновление.

### Подключить одну часть в двух ветках

Найдите ближайшего родителя, который видит обе ветки. Он подключает общий блок, а ветки получают готовый элемент или функцию отрисовки. Например, `App` подключает форму настроек склада и передаёт её складу и админке. Каждая ветка передаёт идентификатор выбранного склада при открытии диалога.

Проверьте, какие данные должны совпадать у обоих экземпляров. Формы читают один ресурс настроек, а свои незавершённые правки хранят отдельно. Если второй потребитель пользуется только теми же данными, достаточно подключить его к ресурсу. Переносить сам интерфейс в общий модуль тогда не требуется.

### Добавить ресурс или действие записи

Сначала проверьте, кто уже читает и меняет этот ресурс. Если ресурс существует, расширьте его публичный контракт и используйте его фабрику ключей. Для нового ресурса определите владельца, параметры ключа кэша и разделение по областям сессии.

У операции записи определите, какие данные она меняет. Владелец обновляет затронутые записи или возвращает их к повторному чтению. Сценарии с конфликтом, потерей ответа и ошибкой чтения после успешной записи проверяются отдельно, если операция может приводить к этим результатам.

## Тесты и проверка архитектуры

- Модульные тесты лежат у владельца поведения. Например, история черновика проверяется в `warehouse-map/model/draft`, сохранение и гонки запросов в `warehouse-data/model/layout`. Связь предпросмотра и редактора проверяет `WarehouseMap.test.tsx`.
- Общие заготовки, включая тестовый порт ресурса, лежат в `tests/support`. Импорт оттуда разрешён тестам и тестовым помощникам. Заготовка зависит от публичного типа порта и доменных типов. Прикладной код не обращается к этим файлам. Сложный тестовый ресурс и его реальный адаптер проверяются по общему контракту, когда тестовый ресурс воспроизводит состояния этого контракта.
- Сетевые гонки проверяются управляемыми ответами. Проверяются старое чтение после подтверждённой записи, смена склада в полёте, потеря ответа и закрытие последней подписки. Геометрия и преобразование координат проверяются отдельно от отрисовки.
- Bun запускает локальные `*.test.ts` и `*.test.tsx`. Браузерные сценарии используют отдельный раннер в `tests/ui`. Тесты интерфейса проверяют видимый результат действия. [Поиск тестов в Bun](https://bun.com/docs/test/discovery), [принципы Testing Library](https://testing-library.com/docs/guiding-principles/), [рекомендации Playwright](https://playwright.dev/docs/best-practices)
- Проверка архитектуры запускается отдельной командой. Она разрешает алиасы и относительные пути, проверяет импорты типов, реэкспорты и ленивые импорты. Пути в подменах модулей, `import.meta.glob` и CSS-импортах тоже проверяются, если они обращаются к файлам проекта. Для динамических путей допускаются статически определимые цели. Проверка сообщает владельца исходного файла, целевой модуль и нарушенное правило.

### Что проверить перед ревью

- По пути нового файла можно найти его владельца. Новые импорты идут к публичным входам, разрешённым правилами модуля.
- У добавленного состояния есть один владелец. Производные значения вычисляются из его данных. Между компонентами видны данные и действия, которыми они обмениваются.
- Если добавлен маршрут, работают прямая ссылка, перезагрузка и ограничения доступа. Если добавлена запись, известны затронутые ресурсы и поведение при ошибке.
- Тест размещён у владельца поведения и проверяет результат. Для связи двух частей проверяется компонент, который их соединяет.
